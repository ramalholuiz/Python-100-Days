# Views, Functions, and Procedures

To explain views, functions, and procedures, we first create an `hrs` database and populate it with sample data using the following DDL and DML:

create table `tb_dept`
(
`dno` int not null comment 'Department ID',

## Views

A view is a relational database object that organizes query result sets into queryable tables. Simply, a view is a virtual table. Unlike real tables (physical structures), views are virtual structures—you can think of them as saved, named SQL statements in a database.

Benefits of using views:

1. Hide actual data tables, preventing external programs from knowing the real data structure. Allow users to access only table portions, not entire tables, reducing database attack risks.
2. Views are mostly read-only (updates have many restrictions), preventing external modifications through views.
3. Reuse SQL statements by wrapping complex queries in views for direct data access, or use views as tables for joins.
4. Return data in different formats than entity tables, applying formatting during view creation.

Create a view:

```sql
create view `vw_emp_simple`
as
select  `eno`,
        `ename`,
        `job`,
        `dno`
  from  `tb_emp`;
```

> **Tip**: Since views don't contain data, executing queries against views is necessary each time. Using complex joins or nested queries in views may significantly impact performance. Test complex views before use to ensure performance meets application needs.

With this view, we can restrict certain users to only access employee information through the view, preventing exposure of sensitive fields like salary (`sal`) and bonuses (`comm`). Query the view:

```sql
select * from `vw_emp_simple`;
```

Results:

```
+------+-----------+--------------+-----+
| eno  | ename     | job          | dno |
+------+-----------+--------------+-----+
| 1359 | Hu Yidao  | Sales Rep    |  30 |
| 2056 | Qiao Feng | Analyst      |  20 |
| ... (more rows) ...
```

Can view data be updated? View updatability depends on the situation. These view types cannot be updated:

1. Views using aggregate functions (`SUM`, `MIN`, `MAX`, `AVG`, `COUNT`), `DISTINCT`, `GROUP BY`, `HAVING`, `UNION`, or `UNION ALL`.
2. Views with subqueries in `SELECT`.
3. Views based on non-updatable views.
4. Views with `WHERE` clause subqueries referencing `FROM` tables.

Delete a view:

```sql
drop view if exists `vw_emp_simple`;
```

> **Note**: To update views, delete them or use `create or replace view`.

View rules and limitations:

1. Views can be nested, building new views from other view data. Views also work with tables.
2. `ORDER BY` can be used in view creation, but `ORDER BY` in queries overrides view's `ORDER BY`.
3. Views don't use indexes and don't trigger triggers.

## Functions

MySQL functions resemble Python functions—both encapsulate reusable, functionally independent code. A key difference: MySQL functions can execute SQL statements. The example below creates a custom function for truncating long strings:

```sql
delimiter $$

create function fn_truncate_string(
    content varchar(10000),
    max_length int unsigned
) returns varchar(10000) no sql
begin
    declare result varchar(10000) default content;
    if char_length(content) > max_length then
        set result = left(content, max_length);
        set result = concat(result, '……');
    end if;
    return result;
end $$

delimiter ;
```

> **Note**: The `no sql` after function declaration indicates no SQL statements in the function body. Use `reads sql data` if the function reads data via SQL.

Call the custom function:

```sql
select fn_truncate_string('Hello world', 5) as short_string;
```

## Stored Procedures

Stored procedures are precompiled groups of SQL statements stored in the database. Calling procedures simplifies developer work, reduces database server communication, and improves operation performance. Unlike single SQL statements we've used, real applications often need multiple statements to complete operations.

The following procedure implements salary increases in the hrs database: Department 10 raises 300, Department 20 raises 800, Department 30 raises 500:

```sql
delimiter $$

create procedure sp_upgrade_salary()
begin
    declare flag boolean default 1;
    -- Define exception handler
    declare continue handler for sqlexception set flag=0;

    -- Start transaction
    start transaction;
    
    update tb_emp set sal=sal+300 where dno=10;
    update tb_emp set sal=sal+800 where dno=20;
    update tb_emp set sal=sal+500 where dno=30;

    -- Commit or rollback transaction
    if flag then
        commit;
    else
        rollback;
    end if;
end $$

delimiter ;
```

Call the procedure:

```sql
call sp_upgrade_salary();
```

Delete the procedure:

```sql
drop procedure if exists sp_upgrade_salary;
```

> **Note**: While procedures offer benefits, frequent use with complex logic can overload database servers, often becoming performance bottlenecks. For internet products, let databases focus on storage while application servers handle complex computations. Scale horizontally with multiple application servers if needed.
