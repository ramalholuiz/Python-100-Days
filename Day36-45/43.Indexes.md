# Indexes

Indexes are the most important means for improving query performance in relational databases. Database indexes resemble book tables of contents—without one, finding a topic means flipping through pages. While indexes consume storage space (like book table of contents), the query time reduction is significant.

All data types in MySQL can be indexed. For MySQL 8.0's InnoDB engine, three index types exist: B+ tree indexes, full-text indexes, and R-tree indexes. We focus on the widely-used B+ tree index since it's the most efficient data structure for large-scale disk storage and sorting. B+ trees are balanced trees with height typically 3-4, capable of storing millions to billions of records. Querying a record requires only 3-4 I/O operations.

B+ trees consist of root, intermediate, and leaf nodes, with leaf nodes storing sorted data. Since index records are sorted, binary search within leaf nodes is highly efficient. When data is sparse, B+ trees have only a root node containing data. As records increase, B+ trees split: root nodes become pointers to lower layers, helping locate data in leaf nodes.

When creating tables, primary key columns get default indexes. For InnoDB (index-organized storage), the primary key index is the entire table's data, called **clustered index**. Tables have only one clustered index. Custom indexes are secondary indexes, commonly called **non-clustered indexes**. Non-clustered indexes locate record primary keys; retrieving actual data may require querying through clustered indexes—this phenomenon is "table lookup," making non-clustered index retrieval slower than clustered index retrieval.

Let's demonstrate index importance with an example—querying students by name, common in practice. Use MySQL's `explain` keyword to view SQL execution plans (database's specific SQL execution steps):

```sql
explain select * from tb_student where stu_name='Yang Guo'\G
```

Without an index, the plan shows:

```
type: ALL
key: NULL
rows: 11
Extra: Using where
```

This indicates full table scan—terrible performance on large tables. Create an index:

```sql
create index idx_student_name on tb_student(stu_name);
```

After creating the index, the plan shows:

```
type: ref
key: idx_student_name
key_len: 62
rows: 1
```

Query now uses the index, scanning only 1 row—significant performance improvement!

MySQL allows prefix indexes (indexing first N characters), reducing index space but potentially wasting time:

```sql
create index idx_student_name_1 on tb_student(stu_name(1));
```

Delete indexes:

```sql
alter table tb_student drop index idx_student_name;
```

Or:

```sql
drop index idx_student_name on tb_student;
```

Index design principles:

1. Best for columns in `WHERE` and join clauses.
2. Higher cardinality (more unique values) makes better indexes.
3. Prefix indexes reduce storage space; more indexes cache in memory.
4. Avoid excessive indexing—while indexes accelerate reads, they slow writes since data changes require index updates.
5. With InnoDB, regular indexes store primary key values. Keep primary keys small for efficient index storage and caching.

InnoDB's B-tree indexes work for numeric columns with `=`, `>`, `<`, `>=`, `<=`, `BETWEEN...AND...`, `<>`. For string columns, non-wildcard prefix pattern matching uses indexes; other cases may cause full table scans.
